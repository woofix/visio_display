# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Visio-Display is a self-hosted digital signage platform (GPL-3.0): a Flask admin UI drives one or more
public display screens, with media management, campaigns, RBAC, kiosk client management and server
self-update. It runs as a Docker Compose stack: **app** (Gunicorn), **worker** (RQ, video encoding),
**redis**, **postgres**, and **updater** (privileged sidecar with access to the Docker socket).

The UI is bilingual French/English; code comments and much of the documentation are in French.

```bash

# Full stack (requires .env: POSTGRES_PASSWORD, DISPLAY_API_TOKEN, UPDATER_API_TOKEN, MEDIA_DIR, PRIVATE_DIR
# — generated by scripts/security_bootstrap.sh). App listens on ${PORT:-8081}.
docker compose up -d --build

# Git hooks (once per machine)
./scripts/install_git_hooks.sh
```

Note: `main.sh` and `dev.sh` are **production update scripts** (git pull + Docker rebuild), not dev servers.

### Versioning pre-commit hook

Each commit auto-bumps `VERSION`: patch by default; **major** when touching `web/db.py`, `Dockerfile`,
requirements files, or deleting any file; **minor** when touching `docker-compose.yml`. Override with
`VISIO_VERSION_BUMP=minor|major|none git commit ...`. The hook also **blocks committing media/runtime
files** (images, videos, `web/static/data/`, etc.) — media lives outside git in `MEDIA_DIR`.

## Architecture

All runtime code lives in `web/`. Layering: **blueprints** (thin routes) → **services** (`*_svc.py`,
business logic) → `db.py` (every SQLAlchemy model in this one file).

- `web/app.py` — Flask factory `create_app()`; all setup steps live in `web/app_bootstrap.py`
  (config, DB init, blueprint registration, request hooks, background threads: encoder scheduler,
  backup scheduler, ephemeris refresh).
- `web/blueprints/` — one file per admin area; settings pages are split under `blueprints/settings/`.
- `web/services/` — business logic. Notably `config_svc.py` (app config is a single JSON blob in the
  `AppConfig` table), `queue_svc.py` (RQ jobs on queues `visio-display:upload` and
  `visio-display:compress`), `updater_client.py`/`updater_server.py` (app ↔ updater sidecar over HTTP
  with `UPDATER_API_TOKEN`).
- Frontend is server-rendered Jinja2 (`web/templates/`) + vanilla JS (`web/static/js/`) — **no build
  step, no npm**. The public display is `templates/index.html` + `static/js/display-screen.js`, gated
  by `DISPLAY_API_TOKEN` (`?screen_token=` URL param). Icons are local Lucide/Tabler SVGs under
  `web/static/assets/`.

### Access-control guard pattern

Routes start with an early-return guard from `web/blueprints/guards.py`:

```python
guard = admin_guard()           # or superadmin_guard, perm_guard('<perm>'), feature_guard('<feature>')
if guard: return guard
```

Guards come in redirect (HTML pages) and `_json` (API) flavors. The one-liner `if guard: return guard`
is intentional — ruff E701 is disabled for it. Follow this pattern for new routes.

### Database and migrations

Production is **PostgreSQL only**; the test suite runs on **SQLite**. There is no migration framework:
migrations are additive column additions declared in `SCHEMA_MIGRATIONS` in `web/app_bootstrap.py` and
applied at app startup — they must stay compatible with both engines.

### i18n

All UI strings live in `web/translations.py` (FR/EN). Use `_trans()` and `_flash()` from
`web/services/i18n.py` — never hardcode user-facing strings in routes or templates.
